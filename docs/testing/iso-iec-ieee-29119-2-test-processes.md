# ISO/IEC/IEEE 29119-2 Test Processes - Lightweight Test Profile

## 1. Purpose

This document defines the lightweight test processes used by Authrim. It is
aligned with the process-oriented intent of ISO/IEC/IEEE 29119-2, while keeping
the operational burden appropriate for a fast-moving authentication platform.

## 2. Process Model

Authrim uses three process layers:

| Layer                       | Purpose                                                                         | Output                                               |
| --------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Organizational test process | Establish common testing policy, risk model, and quality expectations           | test profile, coverage targets, release criteria     |
| Test management process     | Plan, monitor, control, and report test work for a package, feature, or release | package test plan, execution results, summary report |
| Dynamic test process        | Design, implement, execute, evaluate, and maintain concrete tests               | test cases, fixtures, coverage, defects              |

## 3. Organizational Test Process

### 3.1 Establish Test Policy

Authrim testing policy:

- Security-sensitive behavior must be tested with positive and negative cases.
- Authentication and authorization decisions must fail closed.
- Coverage targets apply by package, but critical decisions require explicit
  test design evidence beyond numeric coverage.
- UI packages may use a separate browser and accessibility test strategy.
- Test evidence must be reproducible from repository commands.
- Matrix-driven integration tests and live environment validation are part of
  the product quality baseline when behavior crosses package, deployment, or
  runtime-storage boundaries.

### 3.2 Establish Working Coverage Targets

These are initial working targets, not certification thresholds or customer
service-level commitments. They are intended to keep the solo-maintained
project honest, prevent avoidable regression, and guide prioritization.

| Package group                       |       Line coverage target |            Branch coverage target | Notes                                                     |
| ----------------------------------- | -------------------------: | --------------------------------: | --------------------------------------------------------- |
| Security-sensitive backend packages | 70% minimum, 80% preferred | 60% minimum, increasing over time | decision table evidence required for critical logic       |
| Shared core libraries               | 75% minimum, 85% preferred |                       65% minimum | includes storage, logging, tenant, and security utilities |
| Setup and migration tooling         |                60% minimum |                       50% minimum | risk-based exceptions allowed                             |
| UI packages                         |            separate target |                   separate target | excluded from backend coverage rollups                    |

Targets may be raised only after the test suite is stable enough that the gate
improves quality rather than encouraging shallow tests.

Coverage evaluation rules:

- A package below the working target should have an explicit improvement plan or
  a documented reason why the uncovered code is lower risk.
- Security-sensitive changes should not materially reduce meaningful package
  coverage without an explicit risk note.
- New tests should be judged by whether they would catch plausible protocol,
  tenant, authorization, or privacy regressions.
- Critical decision evidence takes precedence over raw line coverage.

### 3.3 Current Calibration Basis

This profile incorporates the repository shape as of 2026-05-20. It should not
be read as a direct copy of older external-product analysis notes.

Current baseline inputs include:

- package-local Vitest suites across `ar-auth`, `ar-token`, `ar-discovery`,
  `ar-router`, `ar-async`, `ar-management`, `ar-lib-core`, `ar-lib-logging`,
  `ar-saml`, `ar-bridge`, `ar-vc`, and `setup`
- local integration suites under `test/integration`, including protocol,
  discovery, topology, and runtime-storage boundary checks
- machine-readable fixtures under `test/fixtures`, including topology and
  runtime-profile matrices where they remain useful
- environment validation and live smoke runners under `test/environment-validation`
- package coverage reports generated by Vitest and ignored by git

Older comparative analysis remains useful as rationale, but current decisions
should account for the runtime-storage work added since those notes were
written, including single/multi-shard assignments, mixed tenant placement, future external adapter paths,
logging package expansion, generated environment validation, and additional
package-level tests.

### 3.4 Change Quality Rules

For security-sensitive changes:

- add or update tests with the behavior change
- include at least one negative case for unsafe or malformed input where
  applicable
- include a regression test for bug fixes when the failure can be reproduced
  locally
- verify side effects when they are part of the product contract, such as audit
  events, settings history, queue delivery, session state, grant state, webhook
  payloads, or redaction behavior
- avoid changing queue producer payload schemas unless the feature explicitly
  requires it
- document accepted residual risk when a meaningful test cannot be added yet

For coverage-focused work:

- prefer tests that validate externally observable behavior or stable boundary
  contracts
- do not add shallow tests whose only purpose is to execute uncovered lines
- review uncovered lines in critical files before deciding the work is complete
- keep UI coverage separate from backend package coverage unless the task is
  explicitly a UI quality task

### 3.5 Define Critical Decision Areas

The following areas require decision-table or MC/DC-style test design when
logic changes:

- redirect URI validation
- client authentication
- grant type validation
- PKCE validation
- token audience, issuer, expiry, and binding checks
- tenant and issuer resolution
- Origin, Referer, CORS, and CSRF decisions
- admin authorization and role decisions
- scope and consent calculation
- JWK and signing key selection
- logging redaction and audit payload classification

## 4. Test Management Process

### 4.1 Plan

For each meaningful feature or package improvement, identify:

- affected packages
- security-sensitive behavior
- expected test level
- critical decisions requiring tables or matrix tests
- coverage impact
- commands required for verification
- side effects that must be asserted
- whether local integration, live smoke, or browser coverage is required

### 4.2 Monitor and Control

During implementation, maintain:

- passing targeted package tests
- no unrelated producer schema changes unless explicitly required
- no shallow tests added solely to increase coverage
- clear separation between backend and UI coverage work
- review of uncovered lines for critical behavior
- side-effect assertions are included when behavior changes state outside the
  immediate response

### 4.3 Completion Criteria

A testing task is complete when:

- new or changed behavior has meaningful tests
- targeted tests pass
- relevant package coverage has been run
- typecheck has passed for affected packages when practical
- known residual risks are documented
- coverage artifacts are ignored by git

For cross-package behavior, completion should also consider the relevant
integration surface:

- local protocol integration under `test/integration`
- topology, tenant, storage, or runtime matrix tests under `test/integration`
- generated environment validation under `test/environment-validation`
- Playwright or browser tests when page-level behavior is the risk being changed

## 5. Dynamic Test Process

### 5.1 Test Design

Test design uses risk-based selection:

- Use equivalence partitions for structured input validation.
- Use boundary value analysis for expiry, intervals, limits, and pagination.
- Use decision tables for authorization and protocol decisions.
- Use state transition tests for device flow, CIBA, sessions, and token lifecycle.
- Use negative tests for malformed, missing, expired, replayed, or cross-tenant input.
- Use failure injection for storage, Durable Object, queue, and service binding errors.

### 5.2 Test Implementation

Tests should:

- live near the package behavior they verify
- name the behavior and expected result
- avoid implementation-only assertions unless validating a boundary contract
- use deterministic fixtures for keys, clocks, tenants, and clients
- avoid real network dependencies unless the test is explicitly end-to-end
- avoid changing queue producer payload schemas unless the feature requires it

### 5.3 Test Execution

Common commands:

```bash
pnpm test
pnpm --filter @authrim/ar-auth test
pnpm --filter @authrim/ar-token test
pnpm exec vitest run --coverage
pnpm typecheck
```

Package-level coverage is normally run from the package directory:

```bash
cd packages/ar-auth
pnpm exec vitest run --coverage
```

Cross-package and environment checks use the relevant suite:

```bash
pnpm exec vitest run test/integration
pnpm exec tsx test/environment-validation/validate-generated-env.ts --env test
```

### 5.4 Evaluation

Evaluate test results using:

- pass/fail status
- coverage trend
- uncovered critical paths
- defect severity
- quality of assertions
- whether each relevant risk has a positive and negative test

Coverage alone is insufficient for release confidence.

## 6. Defect and Incident Handling

When a defect is found:

- capture the affected package and behavior
- classify the risk category
- add a regression test before or with the fix
- verify the closest package first, then wider suites if the boundary is shared
- document any unresolved risk in the test summary

Security-sensitive defects should receive negative tests that demonstrate the
unsafe behavior is rejected.

## 7. Release Test Summary

Each release or significant internal patch should summarize:

- affected packages
- tests added or changed
- package coverage
- commands run
- known gaps
- risk acceptance notes

## 8. Test Environment Validation

Authrim uses environment validation to complement local tests. Local tests
should remain the default for fast feedback, while live smoke tests validate
generated configuration, deployment wiring, routing, service bindings, and
runtime topology behavior that cannot be fully proven in package tests.

Recommended validation layers:

| Layer                     | Purpose                                                         | Typical trigger                   |
| ------------------------- | --------------------------------------------------------------- | --------------------------------- |
| Package tests             | Fast local ownership of package behavior                        | every relevant change             |
| Local integration tests   | Cross-package protocol, topology, and storage-boundary behavior | before merging related changes    |
| Runtime topology matrices | single/multi-tenant, single/multi-shard, mixed placement, external adapter paths | topology or storage changes |
| Generated env validation  | Setup output and deploy configuration consistency               | test environment deploy           |
| Live smoke tests          | Real Cloudflare routing and resource bindings                   | `develop` merge, nightly, manual  |
| Conformance environment   | Protocol certification-oriented checks                          | `main` merge, scheduled, manual   |
| Demo smoke                | External demo availability with dummy data                      | `main` merge or release candidate |

Live smoke tests should avoid destructive checks against demo environments.
Destructive or stateful validation belongs in test or conformance environments.
