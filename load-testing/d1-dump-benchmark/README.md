# D1 ダンプ・復元ベンチマーク

合成データだけを入れた専用 D1 を作り、SQL ダンプの生成、ダウンロード、アップロード、復元を計測します。エクスポート中は読み書きの遅延と失敗数も記録します。この README は実行方法と測定条件の説明であり、測定結果は含みません。

## 実行

Authrimのリポジトリルートで実行します。Node.js 22 以上、インストール済みの Wrangler、Cloudflare アカウント ID が必要です。認証には既存の Wrangler OAuth 設定、または `CLOUDFLARE_API_TOKEN` を使います。OAuth を使う場合は、先に次のコマンドで認証を確認してください。

```sh
pnpm exec wrangler whoami
```

アカウント ID を `CLOUDFLARE_ACCOUNT_ID` に設定して実行します。`--account-id` でも指定できます。

```sh
node load-testing/d1-dump-benchmark/run.mjs
```

既定値は D1 のサイズ目標が **100、1024、5120 MiB**、繰り返し回数がそれぞれ **3、1、1 回**です。小さく試す場合は両方を指定します。

```sh
node load-testing/d1-dump-benchmark/run.mjs --sizes 100 --repeats 1
```

`authrim-dump-*` という専用名の D1 と認証付き Worker を作ります。D1 の配置ヒントは `apac` ですが、実際の配置場所を保証するものではありません。既存の Authrim データベースは使いません。D1 / Workers の利用量が発生します。

完了すると `results.json` を保存し、専用 Worker と D1 を削除します。各回の SQL ダンプも復元検証後に削除します。`--keep-resources` を付けた場合はクラウドリソースを残します。

測定完了後、次のコマンドで `RESULTS.md` と失敗区間の記録 `outages.json` を生成できます。

```sh
node load-testing/d1-dump-benchmark/report.mjs
```

途中で失敗した場合は、リソース台帳と途中の測定を残して停止します。ログに出た実行 ID を `RUN_ID` に設定すると、再開または削除できます。再開時も同じサイズ・回数の指定を使ってください。完了済みの回は再実行せず、未完了の回は最初から測り直します。

```sh
node load-testing/d1-dump-benchmark/run.mjs --resume "$RUN_ID"
node load-testing/d1-dump-benchmark/run.mjs --resume "$RUN_ID" --cleanup
```

### ディスク容量が足りない場合

通常は SQL ダンプをローカルファイルに保存します。保存中は 64 MiB ごとに空き容量を確認し、512 MiB 未満で停止します。この調査では、5 GiB の D1 を測る途中でダンプの保存が約 1.4 GiB に達した時点で停止しました。この実行が作った途中ダンプだけを削除した後も空き容量は約 1.85 GiB で、見込み約 4.1 GiB のダンプ全体を保存できませんでした。環境や他のユーザーファイルは削除していません。

`--stream` を付けると、最初のダウンロードでバイト数・MD5・SHA-256 を計算し、受信データを破棄します。復元時は同じエクスポートの署名付き URL から再取得し、Mac を経由してインポート用の署名付き R2 URL へ PUT します。SQL ファイルはローカルに保存しません。

```sh
node load-testing/d1-dump-benchmark/run.mjs --resume "$RUN_ID" --stream
```

この調査の再開では、検証済みの 100 MiB / 1 GiB は飛ばし、未完了の 5 GiB だけをストリーム方式で測り直します。`--stream` は未完了の全測定に適用するオプションで、自動的に容量で切り替えるものではありません。通常実行と完了済みの小さいサイズはローカルファイル方式です。ストリーム方式でも SQL ダンプの 5 GiB インポート上限は同じです。

`runs/` は Git の ignore 対象です。アカウント・リソース ID、生成した設定、ログ、台帳、途中のダンプを保存します。デプロイ用シークレットも一時的にこの中へ書き、デプロイ成功後に削除します。失敗時は残る場合があります。秘密情報や `runs/` 内のファイルをコミットしないでください。公開用の `results.json` には認証トークンや署名付き転送 URL を保存しません。

## 測定方法

データは 1 行あたり 1 KiB のランダムな 16 進 TEXT を持つ合成アカウントです。`UNIQUE (tenant, email)` と `(tenant, status, updated_at)` の索引を作ります。16 進文字は 1 バイトあたり 4 ビットの情報量なので、任意のバイナリと同じ圧縮特性にはなりません。これは汎用的な索引付きスキーマで、実際の Authrim スキーマやデータ分布の再現ではありません。

サイズ目標には `D1 meta.size_after` を使います。1 MiB は 2²⁰ バイトです。テーブル・索引を含む D1 のサイズと、生成する SQL ダンプのサイズは別々に記録します。SQL ダンプが 5 GiB を超えた場合、インポートは実行せず停止します。

Wrangler が使うエクスポート・インポートの REST プロトコルを直接呼び出します。CLI の起動時間は測定に含めません。継続ポーリングの間には250ms待機します。待機と通信を含む観測時間であり、Wrangler CLIと厳密に同じ設定での比較ではありません。

| 記録項目           | 含む時間                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------- |
| `exportApiMs`      | 生成要求から完了を観測するまで。API 通信とポーリング待ちを含む                                  |
| `downloadMs`       | ダウンロード、MD5 / SHA-256 の計算。通常はディスク書き込み、`--stream` では受信データの破棄まで |
| `exportTotalMs`    | 生成要求から最初のダウンロード完了まで                                                          |
| `importInitMs`     | インポートの初期化                                                                              |
| `uploadMs`         | 通常はローカルファイルからの PUT。`--stream` では再ダウンロードと PUT を並行して行う時間        |
| `ingestObservedMs` | 転送完了後、取り込み要求から完了を観測するまで。API 通信とポーリング待ちを含む                  |
| `importTotalMs`    | 初期化から取り込み完了まで                                                                      |

各測定の `downloadMode` と `restoreTransferMode` に転送方式を記録します。通常は両方 `local-file`、`--stream` ではそれぞれ `stream-discard` と `signed-url-via-client` です。ストリーム方式の `uploadMs` は再ダウンロードも含むため、Wrangler のローカルファイルからのアップロード時間とは条件が異なります。`ingestObservedMs` は転送時間と分けて記録します。署名付き URL はメモリ内でのみ扱い、結果や台帳には保存しません。

ネットワーク、ローカルディスク、API の待ち時間が含まれるため、サーバー内部の処理時間だけを表す数値ではありません。詳細は [Cloudflare のインポート・エクスポート仕様](https://developers.cloudflare.com/d1/best-practices/import-export-data/) を参照してください。同仕様では、エクスポート中は対象データベースへの他のリクエストがブロックされると説明されています。

## 同時アクセスと復元検証

専用 Worker から、対象 D1 の読み取り・書き込みと、比較用の小さい D1 の読み取りをそれぞれ 1 秒周期で送ります。比較用 D1 には同じスキーマと合成データ 1 行を置きます。読み取りは各リクエストで新しい `first-primary` セッションを使います。対象 D1 の読み取りは主キーで 1 行を確認し、書き込みは専用の `bench_probe` の 1 行だけを更新します。比較用の読み取りは `SELECT 1` です。

各系列のタイムアウトは 90 秒、同時実行は各 8 件、全体で最大 24 件です。上限に達した回数も記録します。10 秒の事前測定、エクスポート、ダウンロード、5 秒の回復期間ごとに、対象・比較用 D1 のリクエスト数、失敗数、タイムアウト数、成功時の p50 / p95 などを集計します。処理境界をまたぐリクエストは両期間に含むため、期間別の件数は単純合算できません。短い停止は 1 秒周期で取りこぼす可能性があり、90 秒を超える待ち時間は測定できません。復元先のインポート中には、この同時アクセス測定を行いません。

復元先は毎回新しい専用 D1 です。行数、ID・更新時刻・ペイロード長の集計、先頭・末尾各 3 行のサンプルを比較し、`PRAGMA quick_check` を実行します。大容量の全体走査が期限を超えた場合、`quickCheck: incomplete` と警告を残します。ダンプファイルの SHA-256 は記録しますが、全レコードを暗号学的に照合する検証ではありません。同時更新する `bench_probe` は比較対象から外します。

ローカルのテストは次のコマンドで実行できます。

```sh
node --test load-testing/d1-dump-benchmark/*.test.mjs
```
